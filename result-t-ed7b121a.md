## Findings

1. **FAIL - cancel fee is not RBF-relative to the stranded transaction, so replacement can be underpriced and leave the queue stuck.** `replace_stalled_nonce` computes the cancel tip from `get_priority_fee()` and the max fee from `get_gas_price()` (`src/wallet.rs:1624`-`src/wallet.rs:1626`); the in-flight ledger stores only nonce/hash/status, not the original fees (`src/inflight.rs:26`-`src/inflight.rs:32`, `src/inflight.rs:36`-`src/inflight.rs:42`). Counter-example: stranded nonce N has tip 10 gwei and maxFee 100 gwei; current network priority fee is 1 gwei and gas price is 20 gwei. With the 12.5% floor, the cancel is signed around tip 1.125 gwei and maxFee 22.5 gwei, below the stranded tx on both dimensions, so a node enforcing RBF will reject it as underpriced. This is a real defect for the incident class because the recovery advertises "replace the stuck nonce"; it should bump from the stuck tx's own fee when that tx is known, or choose a cancel fee that is provably above all known same-nonce candidates.

2. **FAIL - the CAS/race guard does not prevent canceling a newly submitted legitimate transaction at `chain_next`.** The guard is a plain read of `current_nonce()` (`src/wallet.rs:1617`-`src/wallet.rs:1620`), and `current_nonce()` is just `nonce_manager.peek()` (`src/wallet.rs:472`-`src/wallet.rs:475`). No lock or reservation is held through `sign_with_nonce(request, chain_next)` and broadcast (`src/wallet.rs:1634`-`src/wallet.rs:1642`). Counter-example: current local high-water equals `chain_next`, an unresolved same-nonce record exists because it was created via `sign_with_nonce`, and a concurrent liquidation calls `sign()`. `sign()` reserves exactly `chain_next` (`src/wallet.rs:1166`-`src/wallet.rs:1176`) while the cancel path also signs `chain_next` explicitly (`src/wallet.rs:1186`-`src/wallet.rs:1198`, `src/wallet.rs:1634`). If the cancel's fee is higher, it can replace and kill that just-submitted liquidation. The same can happen through recycled gaps because the guard checks `peek`, not `effective_next_nonce()` (`src/nonce.rs:76`-`src/nonce.rs:84`, `src/nonce.rs:187`-`src/nonce.rs:198`).

3. **FAIL - `verify_broadcast` changes the transaction hash but does not return it, so public hash-based confirmation flows can wait on the wrong hash.** The rebroadcast path signs a bumped replacement, computes `send_hash`, broadcasts it, records it in the ledger, and then returns only `Ok(false)` (`src/wallet.rs:1517`-`src/wallet.rs:1547`). The normal wallet APIs return a single hash (`src/wallet.rs:1668`-`src/wallet.rs:1670`, `src/wallet.rs:1874`-`src/wallet.rs:1884`), and `wait_for_confirmation` waits on exactly the hash the caller supplies (`src/wallet.rs:1983`-`src/wallet.rs:1991`). Internally, `prune_consumed` is nonce-based and the ledger stores a hash set, so wallet health survives the new hash (`src/inflight.rs:38`, `src/inflight.rs:151`-`src/inflight.rs:161`). Externally, any caller that keeps the original tx hash and then calls `wait_for_confirmation(original_hash)` will miss the mined bumped tx.

4. **FAIL - the pending/latest proof is not sound under a lagging RPC endpoint.** `replace_stalled_nonce` relies on one `eth_getTransactionCount(..., "latest")` call (`src/wallet.rs:1604`-`src/wallet.rs:1608`; RPC tag shown at `src/rpc.rs:180`-`src/rpc.rs:189`). If the queried endpoint lags while another endpoint or the sequencer has already mined nonce N, this can still read `chain_next == N`, pass the unresolved-ledger gate (`src/wallet.rs:1611`-`src/wallet.rs:1615`), and broadcast a cancel at an already-consumed nonce (`src/wallet.rs:1634`-`src/wallet.rs:1642`). EVM nonce rules prevent the cancel from mining after N is consumed, so the worst outcome is not double-spend; it is a false recovery attempt: likely `"nonce too low"`, or a stale endpoint accepting then dropping it, plus stale ledger/idempotency state if accepted.

5. **FAIL - `bump_u256` does not fully guarantee the documented RBF floor.** For ordinary nonzero fees and sane `bump_bps`, the ceil formula bumps strictly above the input (`src/transaction.rs:29`-`src/transaction.rs:32`), and `with_bumped_fees` bumps both EIP-1559 tip and maxFee (`src/transaction.rs:571`-`src/transaction.rs:577`). Edge cases break the guarantee: fee 0 stays 0 despite the "strictly greater" comment (`src/transaction.rs:26`-`src/transaction.rs:27`), and `v * (10000 + bump_bps)` is unchecked (`src/transaction.rs:31`), so very large `U256` values or extreme `bump_bps` can overflow/wrap/panic depending on primitive semantics. The code also adds `10_000u32 + bump_bps` without guarding `u32` overflow.

6. **FAIL - broadcast failure leaves a phantom unresolved cancel in the ledger.** `sign_with_nonce` records the cancel as signed before any network send (`src/wallet.rs:1186`-`src/wallet.rs:1198`, via `record_signed_without_release` at `src/wallet.rs:1368`-`src/wallet.rs:1375`). If broadcast fails, `replace_stalled_nonce` returns `Err` without `mark_released` (`src/wallet.rs:1660`-`src/wallet.rs:1662`). Idempotency is correct in one sense because `last_stall_replace` is not updated, allowing immediate retry, and no nonce-manager reservation leaks because `sign_with_nonce` does not increment the counter. The ledger state is not sane: it reports an unresolved same-nonce tx hash that never landed and can keep influencing `lowest_unresolved_inflight`.

7. **FAIL - the 3s idempotency window can suppress a needed retry on Base's block cadence.** The window is a fixed 3 seconds (`src/wallet.rs:332`-`src/wallet.rs:335`) and is applied before any RPC health check (`src/wallet.rs:1597`-`src/wallet.rs:1602`). It is only set after a successful broadcast (`src/wallet.rs:1644`-`src/wallet.rs:1648`), so it does not suppress retries after explicit RPC errors. But if the cancel is accepted and then evicted or not propagated, a retry within the next Base block window can be suppressed as `NotStalled`. For a liquidation bot, the window should be tied to observed liveness, block cadence, or returned as a distinct idempotent outcome, not a hard 3s no-op.

8. **FAIL - the tests are too weak to prove the broadcast-path invariants.** The mock server accepts any `eth_sendRawTransaction` and returns a fixed hash without decoding or storing the raw transaction (`src/wallet.rs:2816`-`src/wallet.rs:2825`). `replace_stalled_nonce_broadcasts_cancel_under_inflight` asserts only `Cancelled { nonce: 50 }` and the idempotency marker (`src/wallet.rs:2848`-`src/wallet.rs:2867`); it does not prove the raw cancel was nonce 50, self-transfer, gas 21000, EIP-1559, or fee-bumped. `verify_broadcast_rebroadcasts_bumped_when_tx_vanished` asserts only `Ok(false)` (`src/wallet.rs:2929`-`src/wallet.rs:2955`); an implementation that resent the original tx or used wrong fees would still pass. The unit tests cover fee bump helpers, but the broadcast-path tests are largely vacuous for the safety claims.

9. **PASS - same-nonce mutual exclusion is airtight on canonical EVM execution.** The cancel is signed at `chain_next` (`src/wallet.rs:1634`), and any stranded tx at the head has the same account nonce by definition. EVM account nonce validation allows only the transaction whose nonce equals the sender's current state nonce to execute; once one transaction with nonce N is included, the sender nonce advances to N+1 and another same-sender/same-nonce transaction is invalid. Reorgs can replace history, but in one canonical chain state the stranded tx and cancel cannot both mine.

10. **PASS - ledger double-recording is set-like and does not double-count unresolved nonces.** `sign_with_nonce` first records the signed hash (`src/wallet.rs:1186`-`src/wallet.rs:1198`, `src/wallet.rs:1368`-`src/wallet.rs:1375`), then successful cancel broadcast calls `mark_rebroadcast_accepted` for the same nonce/hash (`src/wallet.rs:1644`-`src/wallet.rs:1648`). The ledger is keyed by nonce and stores hashes in a `BTreeSet` (`src/inflight.rs:38`, `src/inflight.rs:78`-`src/inflight.rs:90`, `src/inflight.rs:172`-`src/inflight.rs:197`), while `unresolved_count` counts records, not hashes (`src/inflight.rs:164`-`src/inflight.rs:169`). `lowest_unresolved_at_or_above` remains one record per nonce (`src/inflight.rs:155`-`src/inflight.rs:161`).

11. **PASS - the self-transfer form is valid for the intended EOA signer on Base/Arbitrum.** The cancel request uses `to == self.address()`, value 0, gas limit 21,000, and empty data (`src/wallet.rs:1628`-`src/wallet.rs:1633`). For a normal externally owned account, this is exactly the intrinsic-gas simple transfer shape and consumes the sender nonce when included. Base and Arbitrum are EVM-compatible and do not reject `to == self`. Caveat: if the sender account had executable/delegated code, 21,000 might not cover execution, but `FastSigner` is a private-key EOA path.

12. **PASS - `sign_with_nonce` not touching the nonce manager is conceptually correct for a replacement.** `sign_with_nonce` explicitly does not increment the internal counter (`src/wallet.rs:1179`-`src/wallet.rs:1198`), which is the right behavior for replacing an already allocated/stranded nonce. The cancel path therefore does not reserve a fresh nonce or create a nonce-manager leak (`src/wallet.rs:1634`). The remaining problem is the ledger error path described above, not the nonce-manager counter.

## Open Questions

- Should `replace_stalled_nonce` return the replacement hash and/or all tracked same-nonce hashes so callers can confirm the actual mined transaction after RBF?
- Can the bot provide the original stranded transaction object or fee tuple to `replace_stalled_nonce`, so the cancel can satisfy RBF relative to the actual same-nonce candidate?

## Verdict

BLOCK. The same-nonce EVM invariant is sound, but the implementation is not nonce-safe enough for a liquidation bot until fee relativity, concurrent same-nonce races, rebroadcast hash propagation, and stale-endpoint proofing are fixed.
